## 2. 실측 결과 ② — 밋밋해 보이는 진짜 원인

그림3이 상용 퀄리티로 안 보이는 이유는 구조 부재가 아니라 **스타일링 부재**다. 정량 실측:

| 항목 | 실측값 | 의미 |

## 4. 재정의된 작업 범위 — 실제로 해야 할 일

### 4-1. 코덱스 작업 (마감 퀄리티의 대부분)

1. **통합 Theme 리소스 신설** — `battle_ui_theme.tres` 1개 생성
   - Panel용 StyleBoxTexture/StyleBoxFlat (테두리·배경)
   - Label용 폰트 지정 → **이미 있는 `assets/font/noto_serif_kr/` 연결** (신규 에셋 불필요)
   - ProgressBar용 StyleBox (아군 청색 / 적군 적색, v2.0 §6-4 기준)
   - 기세 슬롯 활성/비활성 StyleBox

2. **`theme_override` 46개 정리** — 개별 override를 제거하고 Theme으로 통합
   - **이것이 마감 퀄리티 확보의 핵심 작업이다.** 개별 override가 남아 있는 한 톤 일관성(v2.0 §8-1 "전체 디자인 언어의 일관성")은 구조적으로 달성 불가능하다.

3. **기존 기능 노드·Signal 연결은 절대 재작성하지 않는다** (v2.0 §6-1 유지) — 교체 대상은 StyleBox/Font/Texture뿐이다.

## 5. 3-3 "부품별 전체화면 합성 승인" 절차 보완

v2.0 §3-3은 "실제 1920×1080 전투화면에 합성한 상태로 먼저 확인한다"고 규정했다. 원칙은 타당하나 **합성 방법이 명시되어 있지 않아** v2.0 §2-3(절대 금지)과 충돌할 여지가 있다.

**보완 규정:** 여기서의 "합성"은 **이미지 생성 AI에게 화면을 다시 그리게 하는 것이 아니라, 정적 편집 툴(Figma/포토샵 등)에서 실제 게임 스크린샷 위에 제작한 프레임 자산을 레이어로 얹어 확인하는 것**을 의미한다. 또는 Godot에서 직접 적용 후 스크린샷으로 확인한다. 어떤 경우에도 기세 수치·턴 숫자·HP 수치·로그 텍스트가 이미지에 구워진 시안은 승인 대상이 아니다.

## 6. T08-3 상단 HUD 수직 슬라이스 — 실측 반영 실행안

v2.0 §9의 구조를 유지하되, 실측 결과를 반영해 작업 항목을 구체화한다.

### 작업 순서

1. **[코덱스]** `battle_ui_theme.tres` 신설, NotoSerifKR 연결, 상단 HUD 3개 패널(`AllyMomentumHud` / `TurnHud` / `EnemyMomentumHud`)에 Theme 적용
2. **[코덱스]** 상단 HUD 영역의 `theme_override` 제거 → Theme으로 이관
3. **[코덱스]** 기세 슬롯은 우선 StyleBoxFlat(정사각형)으로 활성/비활성 구분 구현 — v2.0 §6-2 허용사항
4. **[김작]** 이 시점 스크린샷과 그림2 상단부 비교 → 폰트/톤만으로 얼마나 근접했는지 1차 판단
5. **[채코치]** 4에서 확인된 격차 기준으로 상단 HUD 전용 프레임 + 중앙 턴 프레임 + 기세 슬롯 아이콘 제작
6. **[코덱스]** 제작 자산을 StyleBoxTexture로 Theme에 연결 (노드 구조 변경 없음)
7. **[QA]** v2.0 §8-2 기능 기준 전항목 확인

**3~4단계를 먼저 두는 이유:** 에셋 제작 전에 Theme+폰트만으로 도달 가능한 수준을 먼저 눈으로 확인하면, 채코치가 만들어야 할 자산의 범위가 훨씬 명확해진다. 지난 실패는 "얼마나 필요한지 모르는 채로 정밀 에셋부터 만들려 한 것"이었으므로, 이 순서를 뒤집지 말 것.

### 성공 기준 (v2.0 §9 유지 + 실측 항목 추가)

1. 아군·적군 각각 10칸, 시작 시 3칸 활성, `3 / 10` 표시 — **기존 구현 회귀 없음 확인**
2. 기세 증감이 슬롯·숫자에 즉시 반영
3. 전체 턴 값이 실제 전투 턴과 일치
4. 상단 HUD 영역 `theme_override` 0건, Theme 리소스 단일 경유
5. 전투화면 Label이 NotoSerifKR로 렌더링됨
6. 기존 전투·고유기·컷인·저장 흐름 무손상 (F6 검증)
7. 김작 비주얼 승인

## 7. 종합 — 왜 이번엔 되는가

지난 시도가 실패한 원인은 실력이나 도구의 한계가 아니라 **이미 존재하는 것을 이미지로 새로 그리려 한 것**이었다. 실측으로 확인된 사실:

- HUD 구조물: **이미 100% 존재** (기세 10칸, 로스터, 정보창, 로그창 전부)
- 기세 데이터 연동: **이미 구현** (`battle_momentum_state.gd`)
- 초상화: **38장 이미 존재**, 512×512 규격 일치
- 폰트: **NotoSerifKR 7종 이미 존재**, 연결만 안 됨
- 그리드/이동범위: **이미 구현**

즉 남은 것은 **Theme 리소스 1개 + 프레임 텍스처 4~5종 + 소형 아이콘 몇 개**이며, 신규 UI 구조 제작은 0건이다. 그림2 수준의 마감은 물량 문제가 아니라 **스타일 통합 작업 한 건**의 문제다.

## 8. 색상·대칭·상태 변형 처리 원칙 (신규 확정)

그림2는 아군(파랑)/적군(빨강)처럼 **같은 문양이 색만 다르거나**, 기세 슬롯처럼 **같은 자리가 상태에 따라 다르게 보여야 하는** 요소가 많다. 이런 요소를 "버전별로 각각 그려달라"고 요청하면 지난 실패와 동일한 패턴(같은 대상을 여러 번 생성 → 미묘한 불일치)이 재발한다. **아래 원칙을 예외 없이 적용한다.**

### 8-1. 원칙: 원본 1장 + Godot 처리로 변형 생성

| 필요 변형 | 잘못된 방법 | 올바른 방법 |
|---|---|---|
| 좌우 대칭 (아군 HUD ↔ 적군 HUD) | 좌/우 각각 그려달라고 요청 | 원본 1장 제작 → Godot에서 `flip_h`(또는 `scale.x = -1`)로 반전 |
| 진영별 색상 (파랑/빨강) | 파랑 버전, 빨강 버전 각각 그려달라고 요청 | **무채색(흰색/회색) 원본 1장**만 제작 → Godot `modulate` 프로퍼티로 아군은 파란 계열, 적군은 빨간 계열 색을 코드에서 입힘 |
| 기세 슬롯 채워짐/빈칸 | 매번 슬롯 상태를 새로 그림 | "빈 칸" 1장 + "채워진 칸" 1장, 총 2장만 제작 → 코드가 현재 기세값만큼 슬롯마다 텍스처 스왑 |
| 채워지는 애니메이션(연출) | 프레임별 그림 여러 장 | 원본 1장 + Godot 셰이더의 fill amount(채움 비율) 파라미터로 좌→우 차오르는 연출 처리 |

**이 표가 의미하는 것:** 채코치가 실제로 그려야 할 장수는 "진영당 1장"이 아니라 "형태당 1장"이다. 색과 좌우는 전부 코드 처리 대상이며, 이미지 생성 요청 목록에 "파랑 버전", "빨강 버전"이 별도 항목으로 올라오면 그 자체가 잘못된 요청이다.

### 8-2. 코덱스 구현 스펙 추가 (§6-2 기세 게이지 보완)

```
[좌우 대칭: 아군 HUD 프레임 텍스처를 적군 HUD에도 동일 사용, TextureRect.flip_h = true]
[진영 색상: 슬롯/프레임 원본은 무채색 1장, modulate로 아군 Color(0.35, 0.55, 1.0) /
            적군 Color(1.0, 0.35, 0.35) 계열 적용 — 정확한 색값은 그림2 스포이드 추출]
[슬롯 상태: empty/filled 텍스처 2장만 요청, 슬롯 10개는 코드에서 반복 배치 후 스왑]
[채움 연출(선택): TextureProgressBar 또는 커스텀 셰이더의 fill amount 사용, 프레임 여러 장 금지]
```

## 9. 그림2→그림3 격차, 그 외 확인된/예상되는 디테일

색·대칭 외에도 그림2 대비 추가로 챙겨야 할 항목들. **전부 이미지 신규 제작이 아니라 Godot 기본 기능(StyleBoxFlat 옵션)이나 데이터 바인딩으로 해결 가능한 항목** 위주로 정리했다.

### 9-1. 둥근 모서리 / 그림자 — 이미지 없이 코드로 해결

그림2의 패널들은 모서리가 둥글고 은은한 그림자가 있다. 이거 이미지로 만들 필요 없다:
- Godot `StyleBoxFlat`은 `corner_radius_*` 4개 프로퍼티로 모서리 둥글기를 직접 지정 가능
- `shadow_size`, `shadow_color`, `shadow_offset`도 `StyleBoxFlat` 자체 기능
- 즉 로그창 배경, 로스터 카드 배경처럼 **단순 사각 패널 + 둥근 모서리 + 그림자**는 프레임 이미지 없이 StyleBoxFlat 설정만으로 그림2 수준 재현 가능. 채코치 요청 목록에서 제외해도 됨.

**전용 이미지가 진짜 필요한 건** 비정형 곡선(중앙 턴 프레임의 잎사귀형 장식 등)과 문양이 들어간 것뿐 — v2.1 §4-2에 이미 정리된 항목 그대로 유지.

### 9-2. 병종 태그 칩 (공병/보병/궁병)

로스터 카드에 있는 "공병/보병/궁병" 색깔 라벨은 **병종 데이터(troop_type)에 따라 색이 바뀌는 기능형 요소**다. 병종별로 이미지를 각각 만들 필요 없이:
- `StyleBoxFlat` 배경색을 troop_type 값에 따라 코드에서 분기 지정 (보병=갈색 계열, 궁병=녹색 계열, 기병=주황 계열 등 — 정확한 색은 그림2에서 추출)
- 텍스트는 Label

### 9-3. 지형 보정 표시 ("산지 110%")

그림2 하단 정보창에 있는 지형 보정 수치는 **전투 데이터와 연동되는 정보**다. 이건 이미지가 아니라 Label + 소형 아이콘(지형 종류별 아이콘 1~2개, 재사용 자산) 조합으로 구현. 그림으로 새로 그릴 대상 아님.

### 9-4. 이동 경로 화살표(→)

그림2 그리드 위에 유닛이 이동할 경로를 화살표로 미리 보여주는 연출이 있다. 이건 **정적 이미지가 아니라 상호작용 기능**이라 별도 확인이 필요하다.

> **확인 필요:** 현재 `MoveRangeOverlayLayer`/`HighlightLayer`(§1 실측 확인됨)에 경로 화살표 프리뷰 기능이 있는지는 이번 실측에서 확인 안 됨. T08-3(상단 HUD) 범위 밖이므로, 이후 "그리드 표현 정돈" 슬라이스(§3-3 실측결과에서 이미 이관 예정으로 명시)에서 함께 감사할 것.

### 9-5. 버튼 (자동전투/턴종료/후퇴)

그림2의 알약형/각진 테두리 버튼도 §4-2 프레임 자산과 같은 원리 — **버튼 배경 프레임 1종만 제작**해서 3개 버튼이 공용으로 쓰면 된다. 버튼마다 다른 프레임 만들 필요 없음(다시 §8-1 "형태당 1장" 원칙 적용).

### 9-6. 폰트 위계 (크기·굵기 차등)

NotoSerifKR을 연결하는 것만으로는 부족하다. 그림2를 보면 이름(굵게, 큼) / 수치(보통, 작음) / 라벨(연하게, 더 작음) 식으로 **폰트 굵기·크기 위계**가 있다. `battle_ui_theme.tres` 안에 최소 3단계(제목용/본문용/보조용) 폰트 사이즈·굵기 변형을 미리 정의해둘 것 — 이것도 이미지 작업 아니고 Theme 설정 작업.

### 9-7. 해상도 대응 (마감 품질 체크 항목)

그림2/3 비교와는 별개로 상용 마감을 노린다면 챙길 것: HUD 패널들의 앵커(anchor)가 고정 픽셀이 아니라 비율 기반으로 잡혀 있는지 확인. 지금은 1920×1080 기준으로만 확인했는데, 다른 해상도에서 깨지는지는 별도 QA 항목으로 T08-3 완료 후 체크.

## 10. 검증 증거와 비교 방법

### 10-1. 동일 조건 스크린샷 원칙

비주얼 개선 전후는 반드시 같은 조건에서 비교한다.

- 해상도: 1920×1080
- 동일 전투 진입 상태
- 동일 아군·적군 편성
- 동일 기세 `3 / 10`
- 동일 전체 턴 `1 / 30`
- 동일 카메라 위치
- 동일 로그·안내 문구 상태

전후 스크린샷의 전투 상태가 다르면 비주얼 개선 효과를 정확히 판정할 수 없으므로 승인 자료로 사용하지 않는다.

### 10-2. 비교 산출물

각 슬라이스는 다음 자료를 남긴다.

1. 변경 전 F6 스크린샷
2. Theme·폰트 1차 적용 후 스크린샷
3. 전용 프레임 적용 후 스크린샷
4. 초안 상단부와의 나란히 비교 이미지
5. 기능 QA 결과
6. 변경 파일 목록과 커밋 SHA

### 10-3. 정량 확인

- 상단 HUD 범위 `theme_override`: 목표 0건
- `StyleBoxTexture`: 승인된 전용 프레임 적용 시 1건 이상
- 전투 Label 기본 폰트 참조: NotoSerifKR 계열 확인
- 기세 슬롯: 아군 10개, 적군 10개
- 시작 활성 슬롯: 각 진영 3개

## 11. 변경 안전장치와 롤백 원칙

### 11-1. 기능 무변경 계약

T08-3A와 T08-3B에서는 다음을 변경하지 않는다.

- 기세 계산 규칙
- 기세 획득·소비 조건
- 턴 진행 규칙
- 장수 데이터
- 고유기 Resolver
- 저장 스키마
- 컷인 재생 계약
- 전투 결과 계산

허용되는 변경은 Theme, Font, StyleBox, Texture, 색상, 여백, 앵커, 시각적 상태 표현에 한정한다.

### 11-2. 작은 커밋 원칙

- Theme·폰트 적용
- override 이관
- 프레임 적용
- 기세 슬롯 아트 적용
- QA 문서 갱신

을 가능한 한 별도 커밋으로 나눈다. 문제가 생기면 해당 시각 변경만 되돌릴 수 있어야 한다.

### 11-3. 롤백 기준

다음 중 하나라도 발생하면 즉시 직전 PASS 커밋으로 되돌린다.

- F6 진입 실패
- 기세 값 또는 슬롯 갱신 불일치
- 컷인 복귀 후 HUD 상태 손실
- 저장·불러오기 후 HUD 값 불일치
- 다른 해상도에서 HUD가 화면 밖으로 이탈
- Theme 적용으로 기존 버튼 입력 영역이 손상

## 13. 에셋 제작 결정 게이트

전용 이미지는 자동으로 제작하지 않는다. 다음 조건을 모두 만족할 때만 제작한다.

1. Theme·폰트만 적용한 스크린샷이 존재한다.
2. 초안과의 남은 격차가 구체적인 형태로 설명된다.
3. StyleBoxFlat만으로 해결 불가능한 비정형 실루엣 또는 문양임이 확인된다.
4. 실제 사용 치수와 9-slice margin이 정해졌다.
5. 텍스트·숫자·상태가 이미지에 포함되지 않는다.
6. 좌우·색상 변형이 별도 이미지가 아니라 Godot 처리로 가능한지 먼저 검토한다.

이 조건을 통과하지 않은 이미지 요청은 보류한다.
