## 1. F1 — S4-3 BASE 동등성 `round_snaps`(시드 6)

### 1-1. 확인한 사실
- 첨부 Linux 다이제스트(시드 4~6)와 골든을 비교했다. 유닛·컨트롤러·로그 4개·쓰기·결과·라운드는 모두 같고, **시드 6 `round_snaps`만** 다르다.
- `round_snaps`는 라운드 시작마다 {유닛, 기세, 로그 4개, **다음 난수 `randf()`**}다(M5-a 하니스 `battle3d_auto_harness.gd:23`). 시드 사이에 로그·유닛은 같고 이 다음 난수 값만 다르다.
- **프레임·연출 난수 가설 반박**: Windows에서 시드 6을 기본·`--fixed-fps 30`·`--fixed-fps 120`으로 돌렸다. 라운드 2~11의 유닛·기세·로그 다이제스트와 다음 난수가 **세 조건 모두 같다**. 시각 효과 난수 호출 수는 프레임에 따라 변하지 않았다(이 전투에서).
- **실제 원인**: 라운드별 다음 난수를 정확한 값으로 찍었다.

  | 라운드 | 비트(float32) | 정확한 값 | Windows Godot JSON | 올바른 15자리 |
  |---|---|---|---|---|
  | 10 | `0x3d29573d` | 0.04134296253323554992675781… | `0.0413429625332356` | `0.0413429625332355` |

  - 나머지 라운드는 15자리 반올림이 경계에 걸리지 않는다.
  - 시드 5의 열 개 값도 확인했다.
- **증명**: Windows `round_snaps` JSON 텍스트에서 `0.0413429625332356`(1번 나옴)만 `0.0413429625332355`로 바꿔 SHA-256을 냈다. 결과 `8e44b0a134d0e1f6…`가 Linux 값과 **정확히 일치**한다. 원래 텍스트는 `88f7d263…`(골든)이다.
- 결론:
  - S4-3 코드와 BASE는 두 환경 모두에서 같다(클코치 확인과 일치).
  - 다른 것은 "실수를 글자로 쓰는 방법"이다. 게임 결과·난수 상태는 두 환경에서 같다.
  - Windows Godot 빌드의 실수 → 문자열 변환이 이 값에서 정확한 반올림과 다르다. 왜 그런지(구현 경로)는 확인하지 않았다(추측: 플랫폼별 C 라이브러리 차이).

## 2. F2 — M5-a2 자동 행동 시작 때 3D가 비어 있지 않음

### 2-1. 재현
- Windows에서 단독·`--fixed-fps 240/1000`으로는 재현되지 않았다.
- 같은 테스트를 **4개 동시에**(CPU 부하) 돌리자 시드 1·2·3 모두에서 재현됐다.
- 수치는 Linux 증거와 **같다**: `cursors [9,2,26,15]`, `sizes [12,2,26,15]`, 첫 실패 지점 동일(일지 80번째).
- 재현 스크립트(커밋 안 함) `evidence/f2/_tmp_f2_spy.gd`, `_tmp_f2_run.gd`. 원문 `evidence/f2/f2_load_*.log`

### 2-2. trace (시드 1, 부하, 프레임 번호 기준)

```
f336 set_phase ally_turn  / tick hold=true ×2      ← 앞 행동 끝, 틱 막힘(정상)
f337 HOLD false (3D _process: 재생·소비 끝)
f337 tick hold=false → ACTION_START idle=true  cursors=[9,2,26,15] sizes=[9,…]
f337 set_phase resolving (anim=true, moves=9)
f337 set_phase facing_select (anim=false, moves=10)
f337 set_phase ally_turn   (anim=false, moves=12)    ← 이동이 프레임을 넘지 않고 끝남
f337 tick hold=false → ACTION_START idle=false cursors=[9,…] sizes=[12,…]   ← 겹침
f338 HOLD true (3D _process가 그제야 봄)
```

- 3D가 hold를 풀면(f337 `_process`) 엔진이 지연 호출로 틱을 돈다. 그 틱의 행동(이동)이 **같은 프레임 안에서** 끝나고 `_set_phase(ally_turn)`이 `call_deferred(_tick_full_auto_battle_if_needed)`를 다시 넣는다. Godot는 지연 호출 처리 중에 들어온 호출도 같은 처리에서 돈다(관찰된 동작). 그래서 두 번째 행동이 3D `_process` 없이 바로 시작된다.
- 클코치 가설("행동이 연출 없이 끝나 hold가 켜지기 전에 다음 행동")이 맞다. 정확히는 "**한 프레임의 지연 호출 처리 안에서 행동 2개가 이어짐**"이다.
- 부하가 있을 때 나오는 이유(추측): 앞 프레임이 길면 이동의 시간 기반 단계(트윈·타이머)가 이미 끝나 있거나 0 길이로 처리된다. 그래서 이동이 같은 처리 안에서 끝난다.
- `test_battle3d_auto_hold_release`가 전체 CI 안에서만 실패하는 것도 같은 현상(부하)이다.

### 2-3. 3D 쓰기 14번째 범위 안에서 해결되는가 → **아니다(사실)**
- 3D 코드는 프레임마다 `_process`에서만 돈다. 엔진의 지연 호출 처리 안에서 3D가 실행될 길이 없다.
- 엔진·이벤트 로그 서비스에 `signal`이 하나도 없다(grep 0). 3D가 이벤트 발생에 즉시 반응할 훅이 없다.
- 3D가 hold를 한순간 풀었다가 바로 다시 거는 방법도 안 된다. 다시 걸면 지연된 틱이 막혀 자동이 영영 멈춘다.
- 그래서 **엔진 쪽 변경이 필요하다** → 지시대로 구현하지 않고 옵션을 적는다.

## 3. F3 — M5-b 재시작 뒤 "0 steps"

### 3-1. 확인한 사실
- Windows 헤드리스는 약 129fps다(측정).
- `--fixed-fps 2000`(프레임당 게임 시간 1/2000초)으로 이 테스트를 돌리면 Windows에서도 같은 항목이 실패한다: "restart 2/3 … (1 steps)".
- trace(재시작한 승리 연습, 4x):

  | 조건 | 첫 스텝 | 두 번째 스텝 시작 | 정리 |
  |---|---|---|---|
  | 기본 | +0프레임 | +25 | +29 |
  | 1/2000초 | +0 | +773 | +1052 |

- 그래서 **"400프레임 뒤 스텝 ≥ 2"는 프레임 속도에 의존하는 대기**다(가설 1 확인). 첫 스텝은 항상 자동 시작 프레임에 나온다.
- **미확인**: Linux가 "0 steps"(1이 아님)라는 점. 이 시뮬레이션에서는 첫 스텝이 늘 바로 시작됐다. 0이면 자동이 시작조차 안 됐거나 첫 틱이 막혔다는 뜻이다. Linux 실행 없이는 F2(hold)와 관계가 있는지 가를 수 없다.

### 3-2. 수정 (커밋 F3)
- `tests/scripts/test_battle3d_scenario_new_battle.gd`:
  - 400프레임 고정 대기 대신 **자동 스텝 2에 도달할 때까지** 기다린다. 상한은 20000프레임이다.
  - 기대값은 그대로다(쓰기 ≥ 2, 스텝 ≥ 2).
  - 실패 문구에 다음을 넣었다: 걸린 프레임 수, 엔진 자동 on/off, hold, 단계, 연출 중 여부, 3D 마지막 자동 문구 2줄.
- 느슨해지는 것은 없다. 상태가 오면 바로 지나가고, 자동이 진행하지 않으면 상한에서 그대로 실패하면서 이유가 찍힌다.
- **Linux에서 다시 돌리면 "0 steps"의 실제 원인이 실패 문구로 나온다.** 그것이 hold 문제면 F2 결정(§2-4)과 함께 처리한다.

- 결과(Windows):
  - 기본: 31 checks 통과, 29초
  - (수정 전 실패 조건): 31 checks 통과, 304초
